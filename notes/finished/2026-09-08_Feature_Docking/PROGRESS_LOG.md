    - **H2 (autoResize interplay) — CONFIRMED, the root cause.** The main demo window is `autoResize: true` (`ImGuiWindowFlags.AlwaysAutoResize`, `DearImGuiKSP/Application/DearImGuiKSP.cs:214`), and the showcase called `DockSpace(DemoDockspaceId, Vector2.zero)`. In `ImGui::DockSpace` a zero size component means "fill the remaining content region": `size.y = max(content_avail.y + size.y, 4.0f)` (imgui.cpp:20831-20836), where `content_avail = ContentRegionRect.Max - CursorPos` (imgui.cpp:12536-12542) and `ContentRegionRect.Max = Min + Size - 2*padding - deco` (imgui.cpp:8635-8638). In an AlwaysAutoResize window `Size` is fitted each frame to the content already submitted, so at the call site (after the last widget) the remaining vertical region is ~0 — the dockspace is clamped to a 4px strip. This is a stable fixed point: `ItemSize(4px)` grows the auto-fit content by 4px, so the next frame's available region is again ~4px (imgui.cpp:20881). Result: a full-width, 4px-tall invisible dockspace; the one-time `ApplyDockLayout` then split that 4px node into ~1.6/2.4px children, so "nothing docks" visibly. Matches the in-game observation exactly.

## Fix chunk — EndChild error when dockspace host is docked (G7 log remediation)
- 2026-09-08: **Root cause confirmed against pinned source and fixed, demo-side only.** In-game G7 (ReformTestInstance) produced one log line: `[ERR] [DearImGuiKSP] DearImGuiKSPNative: ImGui error in window 'DearImGui-KSP Demo': Must call EndChild() and not End()!` while the user was freely docking windows, including the main demo window.
  - **Error path (verified against imgui 1.92.9-docking source):** the message is emitted by `ImGui::End()` at imgui.cpp:8908-8909 — an `IM_ASSERT_USER_ERROR` routed to the native `ErrorCallback` (ContextHost.cpp:109-118, which formats it with `ctx->CurrentWindow`, i.e. the window being ended). It fires when the ended window carries `ImGuiWindowFlags_ChildWindow`, is NOT a `DockNodeHost`, and has `DockIsActive == false` — i.e. ImGui classifies it as a plain child window that must be closed with `EndChild()`.
  - **Why it names 'DearImGui-KSP Demo':** a top-level window only acquires `ChildWindow` through docking — `BeginDocked` ORs `ChildWindow | NoResize` into its flags when the window is bound to a live dock node (imgui.cpp:21532-21544, flags reset every `Begin` at :7956). So the error proves the main demo window — which hosts the demo dockspace — was itself docked into another node. Nothing prevented that: the drag-dock source gate (imgui.cpp:8749) and the drop source/target paths (:21585, :21601) only exclude windows declared `NoDocking`, and the demo window was not. The ChildWindow-without-DockIsActive inconsistency is a transient of dock-node re-parenting: the window-move path clears `DockIsActive` WITHOUT clearing `ChildWindow` (`DockNodeMoveWindows`, imgui.cpp:19031-19036; contrast `DockNodeRemoveWindow` :18941-18943, which clears both), so a frame in which the docked host's node membership is rewritten (merges/teardown during drop processing or node updates) reaches its `End()` in exactly the reported state. Recoverable by design — logged once, state heals on the next `Begin`.
  - **Upstream verdict (hypothesis confirmed):** docking a window that hosts a dockspace into another node is unsupported upstream. The official advanced dockspace demo declares its host window `ImGuiWindowFlags_NoDocking` with the comment "it would be confusing to have two docking targets within each others" (imgui_demo.cpp:10698-10700); `DockSpaceOverViewport`'s host window is likewise `NoDocking` (imgui.cpp:20904). The demo's in-window dockspace host was missing exactly that flag.
  - **Alternative hypothesis ruled out:** no Begin/BeginChild imbalance in demo code — the only `ScrollRegion` (BeginChild) use is in the separate benchmark window (`DearImGuiKSPDemo/BenchmarkUI.cs:146`); the main window scope (DemoConsumer + ThemeDemo) declares no child windows, and all scopes are `using`-paired, so no user-side imbalance exists to trip :8909 without docking.
  - **Fix (`DearImGuiKSPDemo/DemoConsumer.cs`, plus one docs paragraph):** the main window is now declared `ImGuiEx.Window(MainWindowTitle, autoResize: true, noDocking: true)` with an explanatory comment. Per source this closes every path to the error: the window can no longer be drag-docked (source gate imgui.cpp:8749 skips `NoDocking` windows), can no longer receive dock payloads on its title bar (:21601 asserts targets are not `NoDocking`), and if it ever holds a stale `DockId`, `BeginDocked` force-undocks it (`want_undock |= NoDocking`, :21458-21464) — so it can never carry `ChildWindow` at its `End()`. Hosting the dockspace is unaffected (`NoDocking` only excludes the window as a dock participant; upstream's demo hosts a dockspace in a `NoDocking` window), and other windows can still be dropped into the dockspace region inside it (node-level targeting via `DockNodeIsDropAllowedOne`, :19993+, is unchanged). `docs/20-widgets.md` "Window docking" gained a host-window caution line stating the guidance.
